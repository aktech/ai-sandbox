aisb · the per-project agent sandbox

Run AI agents in a box,
not on your laptop.

Claude Code, pi, and friends are powerful and occasionally reckless. aisb drops each one into its own disposable Docker container that can only see the folders you mount in. If the agent goes off the rails, you lose the container, not your home directory.

The blast radius

An agent on your laptop can touch everything.

It has your shell, your SSH keys, your .env files, your whole home directory. One bad rm or a prompt-injected tool call and there is no undo. A sandbox draws a hard line around what the agent can reach.

◇ agent on the host

  • Sees your entire home directory by default
  • Can read SSH keys, tokens, every .env
  • A wrong command hits real files instantly
  • Installed tools pollute your global setup
  • No clean blast radius, so recovery is manual

◆ agent in aisb

  • Sees only the paths you explicitly mount
  • Secrets stay out unless you opt them in
  • Worst case: aisb rm and the mess is gone
  • Tools live in the image, not your machine
  • One container per project, fully isolated

What you get

Isolation that stays out of your way.

One command spins up (or re-enters) a sandbox for the current project and drops you into a shell where the agents are already installed.

[ ]

One box per project

Each directory gets its own named container. Re-running aisb re-enters the same one, so your session survives.

▤

Explicit mounts only

The container sees the project dir and nothing else, until you list more paths. Write src or src:dest.

⌁

Disposable by design

aisb rm and the container is gone. No leftover state, no half-broken global environment to clean up.

⚙

Batteries included

Debian slim with claude, pi, Node, Go, uv, pixi, git, and zsh baked into the image.

⟳

Files stay yours

The container runs as a non-root user whose UID/GID matches the host, so files it creates stay writable from outside.

⧉

Persistent sessions

tmux ships in the image, so long-running agent runs keep going across re-entries and detaches.

Three commands

From zero to sandboxed agent.

Build the binary, build the image once, then live in aisb.

01 / build the CLI

Get aisb on your PATH

Compile the Go binary into ./bin/aisb and put it somewhere on your path.

make build
02 / build the image

One-time image build

Bake the Debian image with the agents and toolchain. Takes a few minutes, once.

aisb build # ~5 min
03 / enter

Drop into the sandbox

From any project, run aisb and start claude or pi as usual.

cd ~/dev/my-project && aisb

Reference

The command surface.

Small on purpose. Everything is scoped to the project directory you run it from.

aisb
Enter the sandbox for the current project.
aisb create
Create the container (mounts + labels) without opening a shell.
aisb stop
Stop the current project's container.
aisb rm
Delete the current project's container.
aisb ls
List all sandboxes.
aisb status
Show one container's status.
aisb build
Rebuild the image.

Install

You need Docker, then two builds.

On macOS, colima works well: run colima start and you have a Docker daemon.

setup.sh
zsh
# 1. clone and build the CLI
git clone https://github.com/aktech/ai-sandbox
cd ai-sandbox
make build              # produces ./bin/aisb
cp bin/aisb /usr/local/bin   # or anywhere on $PATH

# 2. build the image (one-time, ~5 min)
aisb build

# 3. sandbox any project
cd ~/dev/my-project
aisb                   # drops you into zsh, claude + pi ready

Mounts, per-project memory/CPU limits, and image overrides live in ~/.config/ai-sandbox/config.json. See the README for the full config.
